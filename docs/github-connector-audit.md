# GitHub connector authorization and repository operations

## Verified references

- GitHub OAuth scopes: https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps
  `repo` authorizes public/private repository operations within the user's own privileges; `workflow` is separate. Requested scopes are not evidence of granted access. GitHub App authorization does not use OAuth scopes.
- Authenticated repository listing: https://docs.github.com/en/rest/repos/repos#list-repositories-for-the-authenticated-user
  The connector requests `affiliation=owner,collaborator,organization_member` and returns `has_more`/`next_page` from the response Link header. Agents are instructed to continue pages. This avoids the previous silent first-100 repository limit.
- Reference update: https://docs.github.com/en/rest/git/refs#update-a-reference
  Atomic multi-file operations create blobs, a tree and one commit, then PATCH the branch with `force:false`. A fresh expected head is mandatory and checked before object creation and again immediately before pushing. GitHub rejects a concurrent non-fast-forward update. Protected branches/rules and organization policy remain enforced by GitHub.
- OAuth device client reference: https://github.com/cli/cli/blob/eeb44bc432c0107de002dadd34a61b4e2bd15882/internal/authflow/flow.go
  Build-time `GitHubOAuthClientID` remains preferred. Without it, the public GitHub CLI OAuth client `178c6fc778ccc68e1d6a` is used, replacing the prior Copilot GitHub App client whose permission model did not accept requested `repo` scopes. Device flow sends no client secret. The login screen explicitly says the authorization page identifies **GitHub CLI**. This app identity is not presented as a Ze-owned OAuth registration. A Ze-owned OAuth app can be supplied by build configuration.
- Official mark: https://github.com/primer/octicons/blob/b3e95564299217e1bcc6cd07d62e57d74fb9bc09/icons/mark-github-16.svg
  The original SVG is stored in `Assets.xcassets/GitHubMark.imageset/mark-github.svg`; the MIT license is preserved in `docs/third-party/octicons-LICENSE.txt`. Template rendering uses the current foreground color in light/dark modes. The previous SF Symbol cat is removed.

## Actual behavior

The settings entry and page title are `GitHub连接器`. Multiple accounts retain local Keychain storage. The single shared `GitHubScopePolicy` drives device authorization requests, effective-scope validation, missing descriptions and account status. Its finite request and display target is (the first 16 are mandatory; the final four are requested pending verification):

```text
repo workflow delete_repo admin:org admin:org_hook user gist notifications admin:public_key admin:gpg_key admin:ssh_signing_key write:packages delete:packages project codespace codespace:secrets admin:enterprise read:audit_log manage_billing:copilot write:network_configurations
```

The first 16 scopes are the base set from Astra's scope decision: repositories and workflows; repository deletion; organization/team/member and organization webhook management; account profile/email/following; gists and notifications; SSH authentication, GPG and SSH signing public keys; package publishing/reading/deletion; Projects; Codespaces and user secrets configuration. Parent scopes replace redundant children. In particular, `repo` already includes full repository webhook management, including ping and deletion; adding `admin:repo_hook` would not add that capability. `admin:org_hook` is a separate scope. Secrets scopes do not disclose secret plaintext.

The remaining four scopes are kept in `pendingRequirements`/`pendingScopes` and included in `requestedScopes`, but excluded from `requiredScopes`. Their compatibility is still unverified, so missing any or all of them does not block device login when all 16 mandatory scopes are granted. The raw granted scopes are saved as returned; account rows remain restricted (orange), list the exact missing items with “待核验专项”, and retain the reauthorization button:

| Scope | Intended range | Limits and verification status |
| --- | --- | --- |
| `admin:enterprise` | Enterprise management, including runner, billing, read and SCIM scope children | Enterprise role/product required. A parent scope is not evidence that every enterprise endpoint accepts OAuth tokens. In particular, enterprise SCIM provisioning requires the endpoint's supported credential (such as a classic PAT), and is not supplied by this device OAuth login. Current endpoint/client compatibility was not rechecked online. |
| `read:audit_log` | Organization/enterprise audit log reads | Administrator/product eligibility and endpoint token support still apply; actual OAuth client grant and access were not tested. |
| `manage_billing:copilot` | Copilot Business seats/subscriptions | Organization/billing role and product eligibility required; this grants no Copilot chat/inference access. Actual OAuth client grant and access were not tested. |
| `write:network_configurations` | Hosted compute network configuration management | Product eligibility and endpoint token support required; current definition, OAuth client grant and endpoint acceptance were not rechecked online. |

This is a **finite requested OAuth scope set**, not literal complete account permissions. Network access to GitHub documentation failed on this Linux host (egress proxy connection failure); the four special scope/client/endpoint checks therefore remain pending, not certified. References for the pending checks: [scope definitions](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps), [enterprise SCIM](https://docs.github.com/en/enterprise-cloud@latest/rest/enterprise-admin/scim), [audit logs](https://docs.github.com/en/rest/orgs/orgs#get-the-audit-log-for-an-organization), [Copilot billing](https://docs.github.com/en/rest/copilot/copilot-user-management), and [network configurations](https://docs.github.com/en/rest/orgs/network-configurations). If GitHub rejects the authorization request itself, that server error still prevents login; this change only prevents absent pending grants in a successful token response from being treated as local login failures. Actual OAuth app and endpoint compatibility must be verified before promoting any pending scope to mandatory. A successful restricted login is not a complete grant.

OAuth cannot replace credentials required by endpoints that only accept other token types. For example, GitHub Packages registry authentication requires a classic PAT (or a supported workflow `GITHUB_TOKEN`); asking for package scopes here does not supply registry credentials. GitHub App installation/repository permissions and fine-grained PAT selections are separate permission systems. Account roles, organization approval/SSO, endpoint token types, product availability, archive state and branch rules remain enforced. The independent Copilot login still requests only `read:user` and is unchanged. Expanded authorization does not implement any new management tools.

Device login reads `/user`, checks the expected login (case-insensitive) when upgrading an account, and requires the 16 base scopes in `requiredScopes` **before** metadata or Keychain writes. Missing only one or all four pending scopes allows login and persistence, while `state(for:)` still compares against all 20 requested scopes so that restricted status and exact missing descriptions remain visible. `X-OAuth-Scopes` is authoritative when present, including an empty header; only a missing header falls back to token-response scopes. There is no union with the requested set. Missing mandatory grants or unverifiable device grants throw a visible error and keep the sheet open. Cancellation before persistence, refusal, wrong-account login, insufficient mandatory scopes and persistence errors retain the old credentials; synchronous metadata/Keychain rollback is unchanged. Successful reauthorization preserves UUID and creation date.

Manual-token login permits restricted or unverifiable grants after `/user` validation and records its login method. Its targeted update checks the same expected account. Account rows show one of: target satisfied, exact missing scopes, or unable to verify. Fine-grained PAT access must be checked by repository/operation, not inferred from OAuth scopes. Old records without scope/method metadata decode as unknown. Status reflects last observed metadata and does not imply a fresh server-side authorization check. Missing unrelated scopes do not block existing repository tools. Visible buttons offer account reauthorization and token replacement; manual tokens should be adjusted/regenerated on GitHub before pasting again.

The default OAuth identity remains **GitHub CLI**, with a warning that revocation may affect other use of that app. Configured clients show their own app name on GitHub; configure a Ze-owned OAuth App with Device Flow enabled using the existing `GitHubOAuthClientID`/`GITHUB_OAUTH_CLIENT_ID` keys. Both login explanations disclose account/key/deletion and enterprise/product scopes. This wider grant increases the consequences of credential theft even though current tools focus on repositories.

The model has the existing account/list/read/single-file write/delete tools plus:

- `github_repository_info`: actual repository permissions, default branch and selected branch head SHA. An empty/missing branch yields `branch_error`, not a fabricated head.
- `github_commit_push`: JSON array of text additions/updates/deletions committed together. Content includes original whitespace and empty strings. Existing executable modes are preserved unless explicitly changed. Affected tree directories are read without trusting truncated results. The target branch is advanced without force; a changed head fails without a ref write. Loose Git objects may remain when a race or error prevents publication.
- `github_branch_create`: creates a new remote branch from an explicitly supplied full commit SHA; an existing ref is not overwritten.

Writes continue through the app's existing confirmation gate, showing account, repository, branch, commit message and affected paths. Real API errors determine final success; token material is never returned in tool results. Single-file operations retain Contents API SHA conflict checks. The existing file read tool is UTF-8 text oriented and explicitly truncates large responses at 30,000 characters; this change does not claim arbitrary binary cloning or local git checkout. Empty repositories require an initial single-file Contents API commit before Git tree-based commits can read a head.

## Final review corrections

- All single-file read/write/delete endpoints use the same validated Contents path builder before any confirmation or HTTP request. Dot segments, empty segments, absolute paths, backslashes and control characters are rejected. Owner/repository segments also reject dot names and separators; valid hyphen, underscore and dotted repository names remain accepted. The multi-file client reuses file-path validation.
- Inline file reading explicitly requires `encoding:base64`, a declared size no larger than **1 MiB**, exact decoded-size equality and valid UTF-8. `encoding:none` responses and missing/partial content produce an explicit error; they never become successful empty files. A genuine zero-byte base64 file succeeds. Output beyond 30,000 characters is marked with both a notice and `truncated:true`. No `download_url` is followed.
- Account metadata writes now throw instead of logging-and-success. Metadata is atomically written before Keychain changes; a metadata failure leaves credentials unchanged. If an atomic Keychain change fails, the old metadata is restored and the error reaches the login UI. Published account state changes only after both operations succeed. Deletion uses the same ordering and shows a persistent-error alert. If restoring old metadata also fails, the error explicitly requests reauthorization rather than claiming success. Disk and Keychain are separate storage systems; this is synchronous failure recovery, not a cross-storage crash-atomic transaction.
- `scripts/test-github-client.sh` additionally compiles the **entire production gateway** with account and denied-confirmation fixtures. It verifies invalid paths fail before confirmation/network, while valid dotted/hyphenated names and empty write content reach confirmation. Client fixtures exercise encoding:none, size mismatch, the 1 MiB bound, actual empty files, and account persistence ordering/rollback. These newly added cases require the next macOS CI run; Windows structural checks and diff checks alone do not establish their runtime results.
- The two-head-check plus `force:false` protocol rejects ordinary concurrent branch advancement, but is not a server-side expected-SHA compare-and-swap. A concurrent forced rollback to an ancestor between the final GET and PATCH can still permit a fast-forward update. No stronger atomic-CAS claim is made.
